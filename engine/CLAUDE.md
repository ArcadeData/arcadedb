# Engine CLAUDE.md

Guidance for working under `engine/`. This file records things the code does not tell you, or actively misleads you about. It is not a tour of the module - use `Glob` and the package names for that.

## Concurrency: the conflict unit is the PAGE, and two commit-time merges take it back to the record

`PageManager.checkPageVersion()` compares the transaction's page version against `getMostRecentVersionOfPage()`. Any other committed transaction that touched that page raises `ConcurrentModificationException`, **whether or not the records overlap** - `LocalBucket.findAvailableSpace` deliberately packs unrelated records into the same page, and `EdgeLinkedList.add` makes two edges into one supernode touch the same chunk even though appends commute.

Two mechanisms undo that false verdict at commit time, both leader/embedded-only and both running while the file's commit lock is held (see `TransactionContext.commit1stPhase`):

- **`GRAPH_EDGE_APPEND_MERGE`** replays this transaction's in-chunk edge appends on the newer committed edge-list page.
- **`TX_PAGE_SLOT_MERGE`** (#5381, #5279, #5569) replays this transaction's per-slot record writes on the newer committed bucket page: inserts into free slots, updates that stayed **inside** the page - an overwrite of the same size or smaller, or a growth the page could host by shifting the records that follow (`LocalBucket.growRecordInPage`, shared with the replay so both grow a record identically) - and the delete of a plain in-place record (`rebaseRecordDeleteOnPage`), which only zeroes its own slot-table entry. `LocalBucket` also reserves the insert slot per in-flight transaction, so concurrent inserts into one page get different slots (hence different RIDs) instead of all being handed the same one. A page a transaction CREATED is off-limits to every other transaction's allocator until its creator ends (`inFlightNewPages`, #9694): page numbers are handed out in one order and committed in another, so a page still being filled can lie below another transaction's page horizon and reads to it as an empty page. And when a replay measures a page: the allocator's `getAvailableSpaceInPage`/`getFreeSpaceInPage` answer "can a NEW record go here?" and give up without measuring anything once the record count reaches `maxRecordsInPage`, which small records reach with half the page's bytes free - measure with `findContentInsertionOffset` (#8401, #9694).

Since #6129 the merge also covers the shapes a record takes **after it outgrows its page**, each tracked with its own slot *kind* (`TransactionContext.SLOT_KIND_*`) so the replay checks the committed marker and not only the bytes: the CONTENT record behind a placeholder pointer (in place or growing on its own page), the HEAD chunk of a multi-page record, the spill that turns a plain record into that head chunk (its images differ in shape - plain record in, chunk out - and the replay re-establishes the room the spill used: the slot's own footprint, the free tail of the page when it is the last record, and otherwise the same in-page shift the write used, see the placeholder section below), and since #6178 the COLLAPSE back, chunk head in and plain record out.

The head chunk needs one extra guarantee the pre-image check cannot give: it is the only part of a multi-page record that lives on the page being replayed, so a concurrent transaction that rewrote the record only PAST that chunk would be silently dropped. `LocalBucket.offPageContentFingerprint` closes that - a 64-bit FNV-1a of the chain past the head, taken when the record is taken for update (`TransactionContext.addUpdatedRecord`, the same moment the record's page is pinned) and again at commit before the chain is rewritten. Different fingerprints mean the page falls back to the plain retry it took before #6129.

The same function, at the same moment, answers the same question for the other record shape that keeps content off its own page: the CONTENT record behind a placeholder POINTER (#6141). That one is not a merge condition but the *only* conflict detection there is - the slot holds 8 bytes of pointer that an absorbed update never touches, so no page either transaction pinned changes at all - which is why it is taken whether or not the slot merge is enabled, and why a mismatch raises a `ConcurrentModificationException` in `updateRecordInternal` instead of merely poisoning a page.

**Which mechanism protects the tail depends on the isolation level, and only one of them is the fingerprint.** Under `READ_COMMITTED` (the default) `getPage` does not cache, so a transaction's continuation-chunk pages are loaded fresh under the commit lock and can never fail a version check - the fingerprint is the only thing standing between a tail-only concurrent change and a silently dropped write. Measured, by forcing `isChunkChainTailUnchanged` to true: exactly one test goes red, `Issue6129ChunkedSlotMergeTest.aTailOnlyChangeToTheSameChunkedRecordStillConflicts`, and it goes red by *committing*. Under `REPEATABLE_READ` the same caching that makes both fingerprint walks agree - they read the transaction's own cached pages - is what makes the chain pages stale in the modified set, so the ordinary page-version check refuses them instead. Two levels, two mechanisms, one guarantee; the second is pinned by `aTailOnlyChangeToTheSameChunkedRecordStillConflictsUnderRepeatableRead`, which passes with the fingerprint disabled.

**Know what that trades.** For a multi-page record, "two transactions writing the same record always conflict" used to hold absolutely, for the blunt reason that the head chunk's page was poisoned no matter what. It now holds up to a fingerprint collision: ~2^-64 per pair of concurrent updates to one such record whose head chunks are byte-identical. Deliberate collisions are not a threat model here - both colliding tails are content of the same record, so producing one needs write access to it, and whoever has that can overwrite it by committing last anyway. An installation that wants the absolute form back turns `arcadedb.txPageSlotMerge` off and gets unconditional poisoning, at the cost of the false conflicts the whole mechanism exists to remove.

**Reading a multi-page record validates the RECORD, not the pages under it (#6217).** `LocalBucket.loadMultiPageRecord` assembles the chain and then has to establish that what it assembled is one committed state and not a mix of two - under `READ_COMMITTED` nothing is cached, so each chunk is loaded independently and a commit landing between two of those loads would otherwise be assembled into a record that never existed. It used to answer that with the page VERSION of everything the chain touched, which is the same false verdict the whole page above is about, one path over: a version moves when any record on the page moves, and continuation chunks of different records share pages by design, so a reader was failed by writes that had not touched a byte of its own record and raised a `ConcurrentModificationException` after `arcadedb.txRetries` attempts. The version is still the fast path - a page that has not moved cannot hold a chunk that has - but a page that HAS moved is now asked whether the chunk THIS record owns on it is still, byte for byte, the one the read consumed: marker, declared size, next-chunk pointer and content, against a trace kept during the walk. The pointer is the next chunk's own (page, slot), so the chain's SHAPE is checked too, and a chain that gained or lost a chunk, or whose head collapsed back into a plain record, fails it. A byte comparison rather than the fingerprint the commit side uses: the commit side compares two points in TIME and can only carry a number across them, a read holds both images at once. The two `PageManager` counters `chunkChainReadRevalidations` / `chunkChainReadRetries` are the read-path twins of the merge counters - the first is a false conflict that did not happen, the second a read genuinely thrown away.

**Under `REPEATABLE_READ` "every page of the chain is pinned" is NOT a snapshot (#9070).** Pins are taken one page at a time, by whichever read touches the page first, so a head pinned by the read of a neighbour on its page can sit on continuation pages pinned after a commit rewrote the record. Only a chain this transaction already validated on exactly the same (page, version) images (`TransactionContext.getSnapshotChunkChain`) is returned without comparing it to the newest commit. And a read that fails the comparison retries by releasing and re-pinning only the pages it pinned itself (`TransactionContext.unpinPage`), never by assembling from a head read straight from the `PageManager`: such a record is not the one the next read in the transaction finds, which is how a first read returned the new version and the second a mix. A changed chunk on a page held before the read cannot be read any differently: when the transaction never read the record (no snapshot chain, no own write), it owes no image of it, so the read is served the newest committed state assembled through the page manager alone - no pin taken or released, so the neighbour's read stays repeatable - and the content is kept (`TransactionContext.getSnapshotRecordContent`) so every later read of the transaction answers it (#9620). Only a record the transaction DID read, or is writing, is refused with a `ConcurrentModificationException`; an update of a record served that way is refused when it is taken for update, because the held older page of its chain could not take the rewrite at commit anyway.

What still raises a `ConcurrentModificationException`: two transactions writing the **same** record (by design - the byte-for-byte pre-image check catches it and the application must reload), a slot turning into (or being rebuilt from) a placeholder POINTER, the continuation chunks of a multi-page record, and any page its owner poisoned with one of those.

The delete is tracked with a `null` final image in `TransactionContext.SlotRebaseBuffer.finalBody`, which is why `deleteRecordInternal` decides where to poison only **after** reading the record's marker: every non-plain shape (placeholder pointer or content, chunk chain, corrupted slot, and the error fallback) poisons its own page. A slot the transaction both inserted and deleted is skipped at replay - it never existed on the committed page, so checking for a pre-image would invent a conflict.

**A record that outgrows its page keeps its slot, and that is what makes the shapes above replayable.** The head chunk stays inside the REGION its slot owns on the page (`updateMultiPageRecord` only rewrites inside it), and a placeholder content record is an ordinary record on its own page. The continuation chunks are the part that stays out: they are written through inline record-table writes that no slot image accounts for, so `writeMultiPageRecord`/`updateMultiPageRecord` poison every page they land on. Since #6175 that is every page **but** the one holding the record's own head chunk, which the allocator is told to keep off (`findAvailableSpace`'s `avoidPageNumber`, decided by `headChunkPageToAvoid`) whenever the caller declared the head chunk's slot replayable - the allocator used to prefer that page twice over, first by "prioritize the same page" and then by scanning the free-space statistics from the lowest page id up, so a chain routinely came home and poisoned the one page the whole mechanism exists to keep mergeable. The exclusion is off when the head chunk's slot was not declared (a record being created, a spill onto an already-poisoned page): there the page has nothing left to lose and refusing its free tail would only cost space.

That region is **derived from the page, not remembered** (`LocalBucket.headChunkRegionEnd`): it runs from the slot's offset to the next record's offset, or to the page's maximum content size when the head chunk is the page's last record. A chunk header declares its CONTENT length, not its footprint, so the declared size moves in BOTH directions inside the region - down when the record shrinks (which hands the page's free tail back, exactly as an in-place shrink of a plain last record does), and back up when it grows again (#6163). Before that it could only ever go down, and a record that oscillated in size pinned its head chunk to the smallest size it had ever had, pushing the difference into continuation chunks for the rest of its life. Two consequences: the room a shrink released belongs to the page again (`compressPage` closes the hole, an insert can take the tail), so the grow-back is bounded by what the page says NOW; and because the write sized the chunk against the page IT saw, `rebaseRecordOnPage` re-derives the region on the committed page before replaying a longer head chunk - refusing, and sending the transaction to a retry, when a concurrent commit has taken those bytes.

**Since #6178 a record that shrinks back inside that region stops being a chunk chain at all**, which removes the ratchet at its source rather than compensating for it: `collapseChunkChainToRecord` rewrites the slot as a plain record and frees the chain. The two conditions coincide exactly - content that fits the head chunk (13 bytes of header) fits the region as a plain record (at most 5 bytes of size marker) - so **a persisted chunk head always fills its region**, and a head chunk that declares less than it no longer survives an update. Measured: with the collapse disabled, `Issue6163HeadChunkRoomTest` alone drives the grow-back 12 times, all from a head chunk that had ratcheted down to 11 bytes; with it enabled, zero. The #6163 machinery stays - the region can still grow for other reasons, and the replay's refusal is a defence that costs nothing - but it is no longer the routine path, and the corner it guarded (a concurrent commit taking the room a shrink released) is now met by the plain-record growth replay, which can shift the newcomer right instead of having to refuse.

The head chunk is also the biggest single bite anything takes out of a bucket page - a spill of a page's LAST record is given its own footprint plus the whole free tail - and since #6154 it is fed into `updatePageStatistics` like every other chunk, in both directions.

**Only the pages a transaction PINNED can conflict, and a record update pins exactly one of them.** A record update is deferred: `save()` puts the record in `updatedRecords` and `addUpdatedRecord` pins its own page (`fetchPageInTransaction`) right then, but the write itself happens in `commit1stPhase`, after the file's commit lock is taken. Every other page it needs - a placeholder's content page, the continuation chunks of a chain - is therefore loaded *fresh under the lock*, at the newest committed version, so no page-version check can ever fire on it. That is why the merge does not have to fear false conflicts there - and why it cannot rely on MVCC to catch a *true* one either, which is what `offPageContentFingerprint` is for, in both of its uses: the chunk-chain tail, and the content record of a PLACEHOLDER-backed record, where the pointer page is untouched by either writer and the fingerprint is all there is.

`ConcurrentModificationException extends NeedRetryException`, so retry is the designed response. **Retry safety is asymmetric:** on retry an INSERT gets a fresh slot and RID from `findAvailableSpace`, so nothing is overwritten and retrying is safe. For UPDATE, blind retry can overwrite a concurrent write - re-read first.

**Retry does not always run.** The server auto-retry in `DatabaseAbstractHandler` only fires when the request is an atomic single-request command. A client-managed explicit transaction over `RemoteDatabase` spans several HTTP calls, so the commit is not retried and the raw exception reaches the client. If you are reproducing a CME report, establish which of the two shapes the reporter is using before theorizing.

RID is a physical position (`pageNumber * maxRecordsInPage + slot`), which is why the engine tracks pages rather than records in the first place.

## A record that outgrows its page becomes CHUNKS; the placeholder is what is left of the mechanism that came before

The placeholder - an 8-byte pointer in the record's slot and the content on another page - is the pre-chunk spill mechanism. The chunk chain (#332) took over every case it used to serve except one, and `LocalBucket` has exactly one site that still writes a placeholder pointer: the spill branch of `updateRecordInternal`, when the slot cannot reach `MINIMUM_SPACE_FOR_FIRST_CHUNK` (14 bytes - marker, chunk size, next-chunk pointer, one byte of content).

Since #6149 that branch first asks the page for the few bytes it is missing, through the same in-page shift a growth uses (`shiftFollowingRecordsRight`, shared by `growRecordInPage`, the spill, and the commit-time replay of both). Reaching the spill means the page could not host the record's FULL new size, which says nothing about whether it can spare the five-odd bytes between a 9-byte slot and a chunk header - and it usually can. **Only the missing bytes are taken**: those bytes become part of the region the head chunk owns for the life of the record (see above), so a bigger bite would lock page space away from every other record for good.

What is left for the placeholder is a page with **no free tail at all**. No insert can produce one - `getAvailableSpaceInPage` keeps `SPARE_SPACE_FOR_GROWTH` in hand - but a spill can, because the head chunk of a *last* record takes the whole tail. That is how the tests that still need a placeholder build one (`sealFirstPage`, in `Issue6149PlaceholderPrefersChunksTest`, `Issue6129ChunkedSlotMergeTest` and `Issue5279ConcurrentUpdateTest`); filling a page with inserts no longer does it.

The readers stay: existing databases are full of placeholders, and roughly ten branches across scan, check, delete, update, compaction and space accounting resolve them. Only the writer stopped producing new ones - and an existing placeholder converts to a chunk chain by itself the first time its content record can no longer absorb an update, because that rebuild goes through the very same spill branch.

## A walk that follows adjacency entries without reading the edge must still ask whether the edge is there

An adjacency entry is the pair (edge RID, far vertex RID), both inline in the segment, so a walk can follow it without loading a record, and so cannot notice a ghost: an entry whose edge record is gone. The engine's invariant (`GhostEdgeReporter`) is that a ghost is skipped and reported, which the walks that load the edge get for free through the `RecordNotFoundException` they catch. Every walk that does not load it has to ask, or the answer of a query depends on its projection (`RETURN DISTINCT b.name` against `RETURN DISTINCT b.name, size(r)`, #10149) and the anomaly is reported by one spelling only.

The probe is `GhostEdgeReporter.isLiveEntry(database, edgeRid)`: the bucket answers from the slot table, no record is read, no READ_RECORD grant is asked (the edge is never handed out). **Pay it once per vertex reached, not once per entry**: test for a vertex met already first, which turns away most entries. `GraphTraverser.Neighbours` is that shape for the variable-length walks (`getEdges` with `edgesUnread` probes every entry, because each entry is a path there), and `path.subgraphNodes` does the same (#10148). A ghost must not spend the vertex it names: another, live, entry may reach it later.

The stored outgoing list of an undirected hop over a unidirectional type is walked by its entries too (`IncomingEdgeLookup.getIncomingVertices` is what the lookup answers besides it), so `Neighbours.liveEdge()` has an edge RID to probe there as well (#10463).

Not covered, on purpose, and decided in #10463: the fixed-length hop of an anonymous relationship, `getVertices()` and SQL `out()`/`in()`. They follow the entry by contract (`PatternPredicateGhostEdgeTest` pins it, #8537), and so does everything that counts or joins the entries without iterating them: `countEdges` is the length of the list, the fused `count(*)` / degree / triangle operators and the analytical views are built from the adjacency. A probe in `getEdgesKnowingEndpoints` would cover only the one operator that happens to read entries, leave those others answering from the same ghost, and cost one edge page per entry on the commonest expand path (a cold graph pays the I/O), so an answer would differ by which operator the planner picked instead of by what the query asked. The anomaly is repaired, not probed at every read: `CHECK DATABASE ... FIX` prunes the dangling entries (`prunedDanglingEntries`), after which every walk agrees (`Issue10463GhostEntriesAreRepairedNotProbedTest`). A new walk over the entries chooses between the two on this rule: it probes when it already pays per vertex reached (a visited set in front of it), and follows the entry when it is a count or a per-entry hot path.

## LSM index reads must walk newest to oldest at every level

`LSMTreeIndexAbstract.lookupInPageAndAddInResultset` resolves deletions with a **forward-poisoning** `deletedRIDs` set: a tombstone adds its RID, and a live entry is skipped only if its RID is *already* in the set. A tombstone therefore suppresses only what is encountered **after** it in the walk.

So every enclosing loop of the read path must feed pages newest first, and they all do: `LSMTreeIndexMutable.searchInNonCompactedIndex` counts down from `totalPages - 1`, `LSMTreeIndexCompacted.searchInCompactedIndex` walks descending page numbers, values within a page are walked in reverse, and the trailing preceding-leaf read (holding the oldest chunks) correctly runs last.

**If you change any iteration order in the LSM read path, check it against this invariant.** Getting it wrong does not throw. It silently drops live records that were re-added after a tombstone, surfacing only as "the index returns fewer rows than a plain scan".

Reproducing any tombstone-ordering bug requires the remove and the re-add to be in **separate transactions**: within one transaction `TransactionIndexContext` collapses a REMOVE followed by an ADD on the same (key, RID) into a single ADD, so no tombstone is ever written.

## `count(*)` and `count()` take different paths

`count(*)` matches `SelectExecutionPlanner.isCountStar()` and routes to `CountFromTypeStep`, which sums `LocalBucket.count()`. That returns a **cached counter** (`cachedRecordCount`, persisted to `<db>/statistics.json`) plus the transaction delta, not a scan. `count()` and `count(field)` full-scan and are always accurate.

This is deliberate - it keeps `count(*)` O(1). But it means the two forms can disagree if the counter is ever wrong, and it makes `count(*)` the wrong tool when you are verifying correctness in a test. Use `count()` or `count(@rid)` when you need ground truth.

The counter is recomputed only when it reads -1, which happens on a fresh open with no statistics entry and after an unclean shutdown. That recompute path takes the bucket file lock so it cannot interleave with a commit's delta fold.

## Explicit locks must cover every index component file

`LOCK TYPE` / `LOCK BUCKET` collection in `LocalTransactionExplicitLock` iterates `IndexInternal.getFileIds()` (**plural**), matching what `TransactionIndexContext.addFilesToLock` adds to the must-be-locked set. Singular `getFileId()` returns only the mutable component.

This matters as soon as any index has been compacted: an LSM index with a compacted sub-index, or a vector index with its companion graph file, has two or more files. Locking only the mutable makes the commit-time coverage check throw a plain `TransactionException` - which, not being a `NeedRetryException`, `COMMIT RETRY` cannot absorb. Keep the two collections symmetric.

## Compaction threshold is cached at construction

`LSMTreeIndexMutable.minPagesToScheduleACompaction` is read from `INDEX_COMPACTION_MIN_PAGES_SCHEDULE` in the constructor. Changing that config at runtime does **not** affect an existing mutable; only a new one created by `splitIndex()` picks it up.

To disable auto-compaction reliably mid-test: set the config, `database.async().waitCompletion()`, then force `scheduleCompaction()` + `compact()` on each LSM index (this creates a fresh mutable that reads the new value), then `waitCompletion()` again.

## `countEntries()` is O(1) only on `HASH`

On an LSM index it is a full ascending cursor walk. It counts LIVE entries - the value that survives a `next()`, not the call - so tombstones are excluded whether or not a compaction has purged them (#5601). Getting that wrong is easy in this codebase: `LSMTreeIndexCursor.hasNext()` is optimistic, so `next()` answers `null` at the tail of a scan whose remaining keys are all dead, and any `while (hasNext()) { next(); ++n; }` over-counts.

On a dense `LSM_VECTOR`, `countEntries()` is a lock-free popcount over the location index's presence bits - one word per 128 vector ids since #5588 laid the locations out in primitive arrays, where it used to stream a `ConcurrentHashMap` filtering deleted entries. The bounded backend that made concurrent callers serialize on the `locations` monitor was removed with the eviction it existed for (#5559), so the count is unconditionally the live-vector count. On a sparse `LSM_SPARSE_VECTOR` it returns **postings**, not records: a 2-record fixture with 2 dimensions each reports 4. A full-text index counts one entry per analyzed token and a geospatial one per covering cell. `TypeIndex.countEntries()` sums over buckets and inherits whichever applies.

Never call it on a query path. If you need an "is there more?" signal, derive it from the result window or the candidate budget you already have.

## Lock timeouts default to 5 seconds

`EXPLICIT_LOCK_TIMEOUT` and `COMMIT_LOCK_TIMEOUT` both default to 5000 ms (`TX_RETRIES` defaults to 3). When N threads serialize through one type or bucket lock and each held transaction does a WAL commit, per-thread wait grows as `(N-1) * per_tx_time`. On a slow 2-vCPU CI runner that crosses 5 s and `acquireLock` throws, which is a common source of intermittent failures in contention tests.

Both are `SCOPE.DATABASE`, so a test can raise them per-database without polluting the suite. If you do, comment why - a raised timeout turns a future real deadlock into a long hang instead of a fast failure.

## Waiting for the async workers inside a schema frame never ends

An index build (`TypeIndexBuilder`, `BucketIndexBuilder`, `ManualIndexBuilder`) asks `database.waitForAsyncCompletion()` first: everything the async executor was asked to write has to be committed before the scan, or the index silently misses it (#6281). That wait enqueues a marker on every worker and blocks until each has run it, and a worker needs the database WRITE lock to commit its batch. So the wait cannot be asked from inside a frame that holds the lock (`recordFileChanges`, `bulkChange`, `executeInWriteLock`), and it cannot be asked by a thread that holds a quiescence either: the quiescence parks the workers, the marker sits behind the park, and the park is released only after the call that is waiting. Both ended after the 60 s quiesce timeout, with the main thread parked in `waitCompletionOnePass`.

The rules that follow, and what each one did to `CREATE EDGE TYPE X UNIQUE`, the builder and `ALTER TYPE ... WITH unique = true` under a live executor that held a batch (#10537, none of them had a test with one):
- take the quiescence (`database.quiesceAsync()`) BEFORE the frame, in try-with-resources, whenever the frame links a super type that has indexes or builds an index. It is reentrant: a builder reached from under it rides on it;
- `LocalDatabase.waitForAsyncCompletion()` returns at once for a thread that holds a quiescence (`DatabaseAsyncExecutorImpl.isQuiescedByCurrentThread()`), because the quiescence committed every batch before it parked the workers, which is what the wait asks for;
- a database that never touched the async API has no executor, and both calls are free: nothing in a test without one can see this. `Issue10537TypeCreationOneSchemaEntryTest.noRouteStallsWhileTheAsyncExecutorHoldsABatch` starts one and holds a batch on purpose, and its `@Timeout` is a hang detector, not a latency bound.

## An index lookup of a value the key type cannot hold matches nothing

The key of a lookup (an equality, an `IN` element, a range bound) is converted to the declared key type with `Type.convertIndexKeyOrNull`, and for a kind the type cannot hold the conversion does not refuse: it leaves the value as it was (a `LocalDate` for a BOOLEAN key, which the key comparison then casts: `ClassCastException`, or "Comparison between type N and N not supported" for a DATE) or answers `null` (a list for an INTEGER key), which a range bound reads as "no bound" and answers every row (#10541). `Type.canBeIndexLookupKey` / `Type.isReadAsIndexKey` say whether the value is a key of the class (only for the scalar key classes: string, boolean, numbers, temporals), and `LSMTreeIndex.get/iterator/range`, `HashIndex.get` and `FetchFromIndexStep.valuesConvertToIndexKeyTypes` answer "no row" for one that is not. The WRITE side keeps the lenient conversion on purpose (a record holds what it holds, #8090), so do not move the check into `convertKeysToDeclaredTypes`.

What this does not do, and should not try: reproduce the scan. For a range, the scan orders some foreign kinds across kinds by what they convert to (a `LocalDate` against a DECIMAL by its epoch number, a Boolean against a number as 1), because `BinaryComparator.compareTo` has arms for the pairs. An index has one order, one kind, so there it declines (no rows). `Issue10541IndexedOperandKindTest` states the contract over every property type, operand kind and predicate of both languages, with one type indexed and one identical type not: equality and `IN` answer exactly alike, a range may decline for a kind listed in `FOREIGN` and may otherwise only agree. The same grid is where to add a property type or an operand kind. A new index kind with its own `get`/`iterator`/`range` needs the same check, or this test needs a case for it.

An openCypher `IN` whose right side is one value (`x IN $ids`) has to be a list on both paths: `InExpression.listOperand` is the single definition, and `NodeIndexSeek` calls it for the elements `InListValues.isWholeList` marks (the planner knows `IN $ids` from `IN [$a, $b]`, whose items are one key each whatever they resolve to).

## WAL: `currentPageSize` is the content marker, not the physical size

`WALFile` writes `newPage.getContentSize()` into the field read back as `currentPageSize`, while the modified range is validated against `getPhysicalSize()` in `MutablePage.updateModifiedRange`. A valid WAL entry can therefore legitimately have `changesTo >= currentPageSize`, for example when an append extends past the current content marker.

Do not add WAL header validation that assumes `changesTo < currentPageSize`. It passes review and breaks recovery tests. Safe per-page checks are `deltaSize > 0` and `changesFrom >= 0`; memory bounds for delta allocation come from the outer segment-size file check.
