# Issues #7332, #7346, #7354 - three batches, and two silent behaviour changes worth a release note

- <https://github.com/ArcadeData/arcadedb/issues/7332>
- <https://github.com/ArcadeData/arcadedb/issues/7346>
- <https://github.com/ArcadeData/arcadedb/issues/7354>

Most of this batch is invisible to a user: a probe that can now fire, a diagnostic that no longer
prints `null`, a scan bounded to one block. Two changes are not, and this file exists mainly for
them - they are behaviour changes that produce a *different correct answer* rather than an error,
which is the kind that reaches a user through a support ticket rather than through a stack trace.

## Behaviour change 1: a blank column is "not set" on every source

Before, `RecordReader.get()` answered differently by file format for the same blank column:

| source | `nickname` column left blank | `get("nickname")` |
|---|---|---|
| CSV | `1,Alice,` | `null` - property not set |
| JSONL | `{"nickname":""}` | `""` - property set to the empty string |
| XML | `nickname=""` | `""` - property set to the empty string |

`#7269` had already aligned the five typed accessors (`getInt`, `getLong`, `getDouble`,
`getFloatArray`, `getList`) on "empty means not set" and left `get()`, which is the accessor a
**STRING** property routes through. So the same export, converted from CSV to JSONL, imported
differently: an `IS NULL` filter, a mandatory-property check and a `SELECT ... WHERE x = ''` all
changed their answer with the file format.

All three sources now fold an empty value to `null`, through
`GraphImporter.RecordReader.emptyAsNull()`. **A JSONL or XML import that used to store `""` now
stores nothing at all for that property.**

### The consequence with a name: `filter("attr", "")`

`GraphImporter.VertexConfig.filter(attribute, value)` - `"filter": "PostTypeId="` in a JSON
importer config - selects the rows whose attribute equals the value. With an EMPTY value it used to
mean:

- on XML and JSONL: the rows whose attribute is the empty string, which matched;
- on CSV: the rows whose attribute is `""`, which after CSV's own `emptyAsNull` was nothing at all,
  so the filter selected **zero rows, silently**.

It now means *the rows that do not set the attribute*, on all three. That is the reading the two
sources that worked already had, extended to the third, and it is the only reading left once every
source folds empty to null. A config relying on the CSV form selecting nothing will now select the
blank rows instead.

`XmlRowSource`'s child-element path needed one extra turn to get here. It trims child text - which
is right, because pretty-printed XML puts the surrounding newline and indentation inside the element
- and trimming a value that is ONLY whitespace produces `""`, which `emptyAsNull` then drops. But an
empty `<tag/>` already means "not set", and a whitespace-only value is data on every other source.
The trim is therefore applied only when something survives it:

```java
final String trimmed = text.trim();
rec.fields.put(childName, trimmed.isEmpty() ? text : trimmed);
```

with one more distinction, because that is not quite enough on its own: a pretty-printer writes an
empty element across lines as `<tag>\n      </tag>`, whose text is whitespace too, and storing that
raw would put a newline and an indent into the property - neither the value nor "not set". A LINE
BREAK is what separates the two cases. Nobody writes a line break as the value of an element they
also left blank, so whitespace carrying one is layout and the element is unset, while whitespace
without one is a value the row actually states.

So indentation comes off a real value, `<nickname> </nickname>` keeps its space, and both
`<nickname/>` and the two-line form stay unset. `Issue7332BlankValueIsNotSetTest` asserts all four
together, because a naive fix for any one of them breaks another.

## Behaviour change 2: what counts as an RDF file

RDF detection decided "this is RDF" by collecting every character that fell outside `<...>` on the
first line and requiring them all to be equal, with a loop bound of `size() - 1` that tolerated
exactly one trailing character - the `.` of a canonical triple. Two canonical, spec-valid
N-Triples shapes therefore failed:

```
LF,   <s> <p> <o> .                    works
CRLF, <s> <p> <o> .\r\n                the '\r' is a second trailing character -> not RDF
LF,   <s> <p> "hello world" .          a literal object is entirely outside the brackets -> not RDF
```

Both fell through to the CSV fallback and died on `NumberFormatException: For input string:
"<http://a/rel>"` - a message naming neither RDF nor the `-delimiter` workaround that would have
got the user moving.

Detection is now by the shape of the statement. The grammar is written out at the head of
`SourceDiscovery.nTriplesSeparator`; in short, `subject SEP predicate SEP object (SEP '.')?` with
IRI, blank-node and quoted-literal terms, `@lang` and `^^<datatype>` included, and the whole line
has to be consumed by it.

**This is stricter than what it replaces, not looser**, and that is the part with a user-visible
edge: the old test required only that `<` and `>` counts matched, so a single-line XML document
such as `<a>x</a>` satisfied it and was detected as RDF. It is now detected as XML. A file that
genuinely is RDF and was detected before still is - including the comma- and semicolon-separated
forms, because the separator is taken from between the terms rather than fixed to whitespace, and
required to be the same character in both gaps (which is what the uniqueness test was really
testing).

The separator is also handed to the format, which otherwise falls back to a comma and reads a
canonical space-separated file as a single column. That is #7315's defect, reached from the
detection side; PR #7348 fixes it from the delimiter side and the two overlap in this method.

## The rest, briefly

### #7332 item 2 - the shared-endpoint recovery was dead on its own target

With no `http` port declared, a peer's HTTP endpoint is derived as ITS Raft host plus THIS node's
HTTP port. On a cluster whose nodes differ by port rather than by host, that address is this node's
own **for every peer** - so `PeerDialAddress.sharedEndpointOf` withheld it every time (correctly:
dialling ourselves comes straight back) and the capability probe's second pass never had an endpoint
to ask. Every line was individually right and the feature could not work on the shape its own
javadoc named.

`RaftHAServer.getPortOffsetPeerHttpAddress` supplies the only signal left there:
`localHttpPort + (peerRaftPort - localRaftPort)`. It names the peer's listener when the cluster
moves both ports in step (`2424/2480`, `2425/2481`, ...) and names nothing when it does not.

It is a guess, and it is confined to `sharedEndpoint()` - never `httpAddress()`. That confinement is
the whole argument for admitting one: the capability probe is read-only, its reply names its own
author, and it credits a *configured* peer that actually answered - never this node, never a
stranger, never one that already answered for itself. A resync, a verify or a forwarded write still
refuses, unchanged. See `ha-raft/CLAUDE.md`.

### #7332 item 4 - a saved profiler run says what it can and cannot account for

A recording written before #7291 carries no `measuredCount`, so every step in it read as fully timed
and the negative costs that build produced rendered as written. `loadSavedRun` now stamps
`stepTimingComplete=false` on such a file and marks untimed the steps whose total came out
**negative** - the one part that is decidable, since a timed cost never is. Studio says so once at
the top and gains a `Measured` column, so a step timed in 3 of 100 executions no longer shows a
count of 100 beside an average drawn from 3.

### #7354 - the PromQL discovery endpoints no longer materialise the series

`/label/{name}/values` and `/series` answer an O(label cardinality) question and asked it with
`engine.query()`, which merges every shard's full range into one `ArrayList` **and sorts it by
timestamp** - a sort neither loop uses. These are what a Grafana datasource calls to fill its metric
and label pickers, on every dashboard load and every variable refresh.

`iterateQuery()` is not the fix: its javadoc claimed O(shards x block) but the sealed layer
materialises every matching row before returning the iterator, because the read lock has to be
released first. That claim is corrected rather than relied on. `TimeSeriesEngine.forEachRow` is the
third shape - the same block walk, folding into a visitor - and `iterateRange` is now that loop with
an `ArrayList` for a visitor, so the two cannot drift apart.

Two things were deliberately NOT done:

- **The tag dictionary (#5519) is not a shortcut here.** It is append-only with ids never reused and
  is shared by every TAG column of the type, so it holds values no live sample carries and values
  belonging to other columns. Answering from it would change the response.
- **The response order is preserved rather than left to the traversal.** `query()` handed `/series`
  its rows already sorted by timestamp, so the response came out ordered by when each series first
  appears; `forEachRow` visits shard by shard. The handler now carries each combination's earliest
  timestamp and orders by it, with `List#sort`'s stability giving the same tiebreak - one `long` per
  distinct series, not a sort of the range.
