# 7252 / 7253 / 7255 / 7256 - four HA follow-ups from earlier reviews

Four items split out of #7227, #7221 and #7219 rather than folded into the PRs that found them. Three produce
code; one produces a boundary that no code can enforce, and saying so precisely is the deliverable.

## #7252 - no test covered whether a failed `SECURITY_USERS_ENTRY` is replayed after a restart

#7137 made a local write failure of `server-users.jsonl` non-fatal, and #7227 replaced the javadoc promise that
the entry "replays on the next start" with a hedge, because the honest answer is "it depends on snapshot
timing". Nothing pinned either branch, so the hedge was unfalsifiable: a later change that made the replay
deterministic - or removed it - would have left the operator guidance silently wrong in one direction.

`Issue7252SecurityEntryReplayAfterRestartTest` drives a real `ArcadeStateMachine` over real Ratis storage
through the incident (persist failure at index 5, a successful entry at 6) and then restarts it, twice, with the
two runs differing in exactly one step:

| before the restart | marker | `reinitialize()` seeds | entry 5 |
|---|---|---|---|
| `takeSnapshot()` ran (a graceful stop always takes one) | 6 | 6 | never replayed, users file not restored |
| nothing ran (a kill) | none | -1 | replayed, users file written |

The second case also asserts that `.raft/applied-index` still reads 6 while the replay floor is -1 - the
confusion `ha-raft/CLAUDE.md` calls the most common wrong turn in this module.

What models Ratis is one helper, `replayRetainedLog`, which feeds back the retained entries **above the floor
the state machine itself reports**. Reading the floor rather than assuming it is what stops the model passing by
agreeing with itself.

## #7253 - `installSnapshotFromLeader` dereferenced `raftHAServer` eagerly

`resolveSnapshotSource` reads the volatile field into its own local precisely so it can *refuse* instead of
throwing, and two lines later `getClusterToken()` read the field again. The same shape #7221 fixed one branch
away (PR #7249).

Not reachable today - the second read sits after the refusal check, so a field that was already null is refused
before reaching it, and no production caller passes null to `setRaftHAServer`. What was left is the field turning
null *between* the two reads, and `Issue7253SnapshotInstallReadsHAServerOnceTest` drives exactly that: the mocked
HA server clears the state machine's reference as a side effect of the address resolution inside
`PeerDialAddress.resolve`. It fails with a `NullPointerException` on the pre-fix tree and passes on this one.

Swept the rest of the class for the same shape while there. Five methods guarded the field and then re-read it:
`installSnapshotFromLeader`, `notifyLeaderChanged` (eight dereferences after one null check),
`installFromLeaderForBootstrap`, `triggerSnapshotDownload` (whose `downloadAllDatabasesFrom` now takes the token
rather than re-reading the field) and `triggerDatabaseResync` (which read it from inside a task submitted for
later). Every one now reads once into a local and uses that.

## #7255 - negotiation cannot protect a node replaying entries already committed

**Documentation, deliberately.** The gap is real: the Raft log is durable, a delta entry committed while every
peer was capable stays in it, and a node restarted onto a build predating #7211 replays it with a decoder that
cannot see the section - empty `schemaJson`, nothing applied, nothing logged, silent divergence.

Every mechanism proposed for catching it founders on the same fact, and it is worth stating once rather than
rediscovering: **any receiver-side check lives in a build that HAS the decoder, and the node in trouble is one
that does not.** That kills the trailing-bytes refusal (which #7219 already added), a schema fingerprint on the
entry, and a boot-time refusal to start on a log carrying unreadable shapes - all three protect a boundary that
is not this one. Adding any of them would be code that reads like a fix for #7255 and is not.

So the boundary is operational, and it is now written where the three audiences read:

- `ha-raft/CLAUDE.md`, under the capability section, with the reasoning above and its general form: the
  capability ratchet makes an *upgrade* safe and says nothing about a *downgrade*.
- `GlobalConfiguration.HA_SCHEMA_DELTA`'s description, next to "a rolling upgrade needs no sequencing", which is
  the sentence an operator would otherwise read symmetrically.
- `docs/6989-ha-schema-entry-delta.md`, the feature writeup.

> A cluster whose Raft log has ever carried a schema-delta entry cannot be rolled back past #7211. A node that
> must go back that far is rebuilt from a snapshot - databases reinstalled from a current leader, Raft storage
> discarded - rather than restarted on its retained log.

## #7256 - an ambiguous address made capability negotiation permanently unreachable

On a cluster that declares no `http` ports and whose nodes differ by port, every peer's endpoint derives onto one
address (#6202, #6267). `PeerDialAddress` withholds it, the capability probe never runs, and the leader treats
every such peer as incapable forever. It fails the safe way, which is why nothing complained - but #6989's
benefit is simply unreachable on that deployment shape, with only a throttled INFO line to say so.

### The fix, and why it is safe

The capability probe is **the one peer RPC that may dial an address identifying no single peer**, because it is
read-only and its reply names its own author - the check `PeerCapabilityQuery.parse` already made. So the answer
can be bound to whoever gave it instead of to whoever it was meant for:

1. `PeerDialAddress` now says *which* refusal it is. A new `sharedEndpoint()` carries the address when two or
   more peers resolve to it, and is `null` when there is no address at all or when it is this node's own.
2. `PeerCapabilityQuery.fetchFromSharedEndpoint` asks that address with no expected peer id.
3. `RaftHAServer.refreshPeerCapabilities` runs two passes: the guarded probes as before, then one probe per
   *distinct* withheld address, crediting the answer to whichever configured peer answered.

Three conditions on the answerer, each invisible when it misfires and each pinned by a test: it must name a peer
of the current configuration, it must not be this node, and it must not already have answered for itself in the
first pass - a peer with an unambiguous address of its own is not the peer living behind a collapsed one.
Everything the fan-out cannot account for stays a "no", so the mechanism still fails the cheap way: a withheld
section costs one larger Raft entry, a wrongly-written one costs a silent divergence.

### And it is now visible

`PeerCapabilityRegistry` keeps the reason a peer counts as incapable, and `GET /api/v1/cluster` reports it as
`capabilitiesUnknownReason` on the leader. An absent `capabilities` field used to read the same whether a peer
ran an older build or was never asked at all, and the remedies for those are nothing alike - "finish the
upgrade" against "declare each node's `http` port" (#6202).

`RaftHAServer.CapabilityProber` is a test seam, not a strategy: the fan-out's whole point is *which peer an
answer is credited to*, and pinning that needed a mixed-address cluster and a network otherwise.
